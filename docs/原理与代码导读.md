# 原理与代码导读

IgdOpRegion 是一个用于 QEMU 核显直通场景的 X64 UEFI 辅助驱动。它取得 QEMU 提供的 Intel OpRegion 数据，在客体内存中保存完整副本，再把副本地址写入核显的 ASLS。驱动封装为 PCI Option ROM，由客体固件在操作系统启动前执行。

仓库支持在 macOS 上交叉编译。本文以 Mac 构建、PVE/QEMU 宿主机和 OVMF 客体固件为例，解释代码与启动环境的关系。具体适用条件、已验证配置及证据边界见 [兼容性与验证](兼容性与验证.md)。

本文面向已经掌握普通 C、尚不熟悉 UEFI 或虚拟机启动过程的读者。阅读顺序是“谁运行代码 → 怎样取得设备 → 怎样交接数据”，然后把这条路径对应到三个 C 文件。

## 1. 构建机、宿主机和客体分别做什么

这里有三个执行环境。Mac 是构建机：编译器和封装工具在这里运行，产物是文件。PVE 是宿主机：它运行 QEMU，管理虚拟机和设备直通。虚拟机是客体：其中的 OVMF 固件加载本项目的 EFI 驱动，之后才启动 Windows 或 Linux。

OVMF 是适用于 QEMU 虚拟机的 UEFI 固件。可以把它理解为虚拟机启动时先运行的一套固件程序。它负责发现设备、分配启动阶段资源、加载可执行映像，并把控制权交给操作系统。

平时说的 BIOS 常被用来泛指主板启动固件；UEFI 是现代固件的接口规范。DXE 是固件启动过程中加载驱动、建立设备服务的阶段。本项目的 `DXE_DRIVER` 在这个阶段的服务环境下工作，此时还没有 Windows 的进程、文件 API 或显卡驱动，不能直接使用 `printf()`、`malloc()` 或 Win32 API。

```text
Mac：C 源码 → X64 EFI 驱动 → PCI ROM 文件
                                 │ 提供给虚拟机的 PCI 设备
                                 ▼
PVE：QEMU 创建客体硬件环境和 fw_cfg 数据
                                 │
                                 ▼
客体：OVMF 枚举 PCI → 执行 ROM 中的 EFI → 启动操作系统
```

C 源码中的内存地址、PCI 设备句柄和 UEFI 服务，都是客体固件环境里的对象。ASLS 中最终保存的也是客体物理地址。构建机的指针、宿主机进程地址和客体物理地址属于不同的执行环境；追踪代码中的地址时，需要同时确定它属于哪一层。

本项目采用 QEMU 为该核显提供一个 `etc/igd-opregion` 数据项的环境约定。这个名称没有区分多个 GPU 的信息；代码虽然取得了自身所属设备，数据来源仍是单个 IGD 的交接约定。

## 2. 固件怎样从 ROM 走到 C 入口

PCI 设备可以提供 Option ROM。这里的 `.rom` 是 QEMU 向客体 PCI 设备提供的 ROM 内容文件。固件读取它的头部，找到其中的 EFI 可执行映像，再调用映像入口。

ROM 原意是只读存储器，这里交付的则是用于提供 ROM 内容的普通文件。构建和封装只生成该文件，不涉及显卡或主板固件烧录。可执行行为由 C 源码定义，文件头由 `EfiRom` 生成。这个辅助程序与主板启动固件、负责固件图形输出的 GOP、操作系统显卡驱动分别承担不同职责。

固定 EDK II 的 PCI 总线驱动先给这个 PCI 设备安装 `EFI_PCI_IO_PROTOCOL` 和设备路径，再加载它的 ROM。因此，当本项目的入口运行时，承载 ROM 的设备已经有可用的 PCI 接口。初始化可以同步完成。

```text
PCI 枚举
  → 建立 PCI 设备句柄，安装 PCI_IO
  → 从该设备的 ROM 取出 EFI 映像
  → 调用 IgdOpRegionEntry(ImageHandle, SystemTable)
  → 取得该映像所属设备的 PCI_IO
  → 复制、校验 OpRegion，写入并读回 ASLS
  → 返回状态，固件继续启动
```

这里的入口不是 C 的 `main()`。EDK II 根据 INF 声明生成启动包装代码，再转入 `IgdOpRegionEntry()`。`ImageHandle` 标识当前加载的 EFI 映像，`SystemTable` 提供固件服务表。返回的 `EFI_STATUS` 表示入口执行的结果。

源码依据：[安装设备协议和加载 ROM](https://github.com/tianocore/edk2/blob/2970e5699ba6267f3384ffab20f96647578aebc8/MdeModulePkg/Bus/Pci/PciBusDxe/PciDeviceSupport.c#L217-L340)。

## 3. 句柄、协议和函数指针怎样连接

UEFI 的 handle 是固件管理的对象标识；使用者把它交给固件查找接口，通常不直接解引用它。一个 handle 可以同时拥有多个 protocol。protocol 在这里表示一个功能接口，C 中通常表现为结构体，结构体内包含数据和函数指针。

本项目先从当前 `ImageHandle` 取得 `EFI_LOADED_IMAGE_PROTOCOL`，再使用其 `DeviceHandle` 取得 `EFI_PCI_IO_PROTOCOL`。前者说明映像从哪个设备加载；后者提供这个 PCI 设备的访问方法。

例如：

```c
PciIo->Pci.Read (PciIo, EfiPciIoWidthUint32, 0xfc, 1, &Value);
```

可以按普通 C 的函数指针调用理解：`Pci.Read` 指向固件实现的读取函数；第一个 `PciIo` 参数指明接口实例；后面依次给出访问宽度、配置空间偏移、元素数量和结果缓冲区。`Uint32` 与数量 `1` 合起来表示读取一个 32 位值。

`gBS` 指向 UEFI Boot Services 表。查找协议、分配内存等函数也通过这个表调用。它们在操作系统接管前可用，和操作系统中的标准库、设备文件接口有不同的生命周期。

源码中的 `UINT8/UINT16/UINT32/UINT64` 是固定宽度的无符号整数，类似 `<stdint.h>` 的对应类型；`UINTN` 随目标指针宽度变化。`IN`、`OUT` 只是标注参数方向的宏，不改变 C 的传值规则。`EFI_ERROR(Status)` 用来判断 UEFI 状态值，不能简单以 `Status == -1` 判断失败。

函数声明中的 `EFIAPI` 指定 UEFI 要求的调用约定。调用约定决定参数怎样放进寄存器或栈、谁负责保存哪些寄存器。Mac 上使用的编译器必须生成客体 X64 UEFI 所需的调用形式；C 文件语法相同，并不能省略这层约定。

### 怎样取得“自己的设备”

项目要求 ROM 附属于提供该 OpRegion 数据的目标 IGD。入口只取得 `LoadedImage->DeviceHandle` 上的 PCI_IO，再调用交接函数；设备归属来自实际的 ROM 加载上下文。当前代码不检查厂商、设备型号或显示设备类别，也不遍历所有 PCI 设备挑选核显。正确的设备绑定是调用环境必须满足的前提。

PCI 是系统识别和访问设备的一套标准。BDF 是总线号、设备号、功能号组成的位置编号，如 `02:00.0`；Vendor/Device ID 是厂商和型号编号。位置与型号都不同于这里的固件 handle。使用 handle 可以跟随实际加载上下文，而不用猜测客体分配了什么位置。

在固定 EDK II 的正常 PCI ROM 加载路径中，固件把“PCI 设备路径 + ROM 内偏移”交给 `LoadImage()`，由承载设备上的 LoadFile2 接口取得映像，随后将该设备写入 `LoadedImage.DeviceHandle`。这就是入口能找到自身设备的依据。

取得接口仍可能失败，因此入口保留协议查询的错误处理。它把固件返回的错误状态交给调用者，成功取得有效 PCI_IO 后才进入交接函数。后者可以直接使用这个接口，无需再重复检查调用者已经保证的输入。

源码依据：[ROM 映像的设备路径](https://github.com/tianocore/edk2/blob/2970e5699ba6267f3384ffab20f96647578aebc8/MdeModulePkg/Bus/Pci/PciBusDxe/PciOptionRomSupport.c#L723-L748)、[加载时查找设备](https://github.com/tianocore/edk2/blob/2970e5699ba6267f3384ffab20f96647578aebc8/MdeModulePkg/Core/Dxe/Image/Image.c#L1195-L1239)、[保存 DeviceHandle](https://github.com/tianocore/edk2/blob/2970e5699ba6267f3384ffab20f96647578aebc8/MdeModulePkg/Core/Dxe/Image/Image.c#L1340-L1359)。

## 4. OpRegion 数据为什么需要“搬家”

QEMU 的 `fw_cfg` 是向客体固件提供配置数据的接口。`QemuFwCfgLib` 封装了查询、选择和读取操作。`etc/igd-opregion` 是接口中的数据项名称；读取它，得到的是一段二进制数据。

OpRegion 是 Intel 固件与图形驱动约定的数据区域。其开头包含 `IntelGraphicsMem` 签名、声明大小、版本和 mailbox 信息。mailbox 是区域内按用途划分的固定部分。显示配置数据 VBT（Video BIOS Table）可以放在区域内部，也可以位于其后的扩展数据中。VBT 内部还有 BDB（BIOS Data Blocks）组织的配置记录。

操作系统驱动需要通过核显的 ASLS 找到 OpRegion。ASLS 位于 PCI 配置空间偏移 `0xfc`，保存一个地址。于是本项目必须先取得数据、给数据安排持续有效的内存，最后才把地址交给设备。

“PCI 配置空间”可以理解为设备的一组配置寄存器，不能当普通 RAM 随意读写。`PciIo->Pci.Read/Write` 会完成对应的设备访问。`0xfc` 是这组寄存器内部的字节偏移，不是要直接解引用的内存地址；该寄存器里保存的值才是 OpRegion 的内存地址。GPU BAR 描述的显存或寄存器窗口又是另一类资源，本项目不重新配置它们。

```text
etc/igd-opregion
  → 查询长度
  → 分配客体 ACPI NVS 页
  → 复制完整 blob
  → 验证 OpRegion、VBT 和 BDB 的结构范围
  → 写 ASLS
  → 读回核对，保留这些页
```

当前代码先将 blob 长度限制在 8 KiB～1 MiB，再分配内存。必须复制整个 blob。若扩展 VBT 位于最初 8 KiB 之后，只复制前面的固定区域，会留下无法读取的显示配置。OpRegion 2.1 及以后用相对基址的 RVDA 表示扩展 VBT 位置；完整复制能保持这种偏移关系。2.0 的外置 RVDA 是绝对地址，当前实现对这种形式返回不支持。

blob 是“一段字节数据”的简称。OpRegion/VBT 经宿主平台和 QEMU 提供给客体；驱动保留其内容，在客体内安排有效的副本和指针。数据的采集来源、结构检查和实际显示配置是否正确，属于需要分别确认的环节。

## 5. 64 位程序为什么分配低于 4 GiB 的内存

这里有三个不同的“宽度”：EFI 映像的 CPU 架构、C 变量的类型宽度，以及硬件字段能够保存的地址宽度。

本项目生成 X64 EFI，CPU 可以运行 64 位代码，指针和 `UINTN` 也按 X64 宽度使用。但 ASLS 只有 32 位，因此它能表示的最大地址是 `0xffffffff`。如果分配到更高位置，把地址转换成 `UINT32` 会丢失高位。

代码使用 `AllocateMaxAddress`，将上限设为 `BASE_4GB - 1`，要求整个分配落在 4 GiB 以下。然后才能把分配结果转换为 ASLS 要求的 32 位值。这是寄存器地址宽度对数据位置的约束，与 CPU 能执行多少位指令分别判断。

UEFI 按页分配内存，一页为 4096 字节。`EFI_SIZE_TO_PAGES(Size)` 把字节数向上取整到页数。例如 8200 字节需要三页。复制数据前清零整个分配区，可以让最后一页未使用的部分保持为零。最大 blob 大小默认限制为 1 MiB，这是项目采用的分配上限。

### 为什么使用 ACPI NVS，以及何时可以释放

OpRegion 要在入口返回后继续供操作系统使用。代码采用 `EfiACPIMemoryNVS`，让 UEFI 内存图将这些页标记为 ACPI NVS 保留区；操作系统据此保留它们，而不是将其当作普通可用 RAM。

内存生命周期以“是否尝试发布 ASLS”为分界：

| 阶段 | 设备是否可能持有新地址 | 处理方式 |
|---|---|---|
| 分配或数据校验失败，尚未写 ASLS | 没有 | 已分配的页可以释放 |
| 已尝试写 ASLS | 可能有 | 保留 NVS，包含写入返回错误的情况 |
| 写入后读回失败或值不一致 | 无法确认 | 保留 NVS，并返回错误 |
| 写入与读回一致 | 已交接 | 保留 NVS供后续软件使用 |

后两类错误不能简单套用“错误就 free”的习惯。设备可能已经接受了地址，释放内存会让地址指向后来被复用的页。初始化代码的执行寿命和这段数据的使用寿命要分开考虑。

每次入口都会重新分配本轮启动的 NVS、复制完整数据并写入 ASLS，不读取或复用旧 ASLS。原因是普通客体重启可能保留寄存器中的地址数值，却重新建立 UEFI 内存图；上一轮的数据即使仍可读，也不能据此认定它在本轮仍被保留。旧地址不是本轮函数分配的内存，因此也不能拿它调用 `FreePages()`。

普通重启后，上一轮的页分配记录不会作为本轮的永久保留区继承，所以每次重新交接不会跨重启累积占用。正常 Option ROM 加载路径每轮启动完成一次交接，本项目不增加同轮重复调用检测。

## 6. 三个 C 文件怎样配合

先看 [模块 INF](../src/IgdOpRegionPkg/IgdOpRegion.inf) 的入口、源文件和依赖，再看 [平台 DSC](../src/IgdOpRegionPkg/IgdOpRegion.dsc) 的 X64 目标和库实现映射。之后按下表阅读源码：

| 文件与函数 | 职责 | 阅读时追踪的对象 |
|---|---|---|
| [IgdOpRegion.c](../src/IgdOpRegionPkg/IgdOpRegion.c)：`IgdOpRegionEntry()` | 从当前映像取得所属 PCI 设备接口，再调用交接函数 | `ImageHandle` → `LoadedImage` → `DeviceHandle` → `PciIo` |
| [OpRegion.c](../src/IgdOpRegionPkg/OpRegion.c)：`IgdOpRegionAssign()` | 查询 fw_cfg、分配和复制数据、发布地址并读回 | blob 大小、页数、本轮分配地址、新 ASLS |
| [Validate.c](../src/IgdOpRegionPkg/Validate.c)：`IgdOpRegionValidate()` | 只读取给定缓冲区及其长度，验证数据结构 | 每个偏移、声明长度与边界；校验和仅作诊断 |

[OpRegion.h](../src/IgdOpRegionPkg/OpRegion.h) 声明交接接口和分配上限；[Validate.h](../src/IgdOpRegionPkg/Validate.h) 声明纯数据校验接口。`Validate.c` 不依赖设备、fw_cfg 或页分配，因此能够用普通数据样本单独检查其行为。正确绑定设备保证的是写入对象；数据是否完整、地址是否满足 ASLS 的宽度、内存能否持续有效，仍由交接与校验模块处理。

验证函数先确认 OpRegion 签名和声明范围，再按内嵌或外置位置找到 VBT。内嵌 VBT 限制在 6 KiB 的 mailbox 范围内；外置 VBT 需要检查 RVDA/RVDS 与整个缓冲区的关系。VBT 必须满足最小 48 字节头部、头部大小和表大小边界。内部 BDB 需要符合签名、最小 22 字节头部及其声明范围。

### VBT 校验和：诊断与拒绝条件分开处理

VBT 的字节校验和包含校验和字段本身：把表中所有字节相加并取低 8 位，预期结果为零。当前 `ValidateVbt()` 会计算这个值，但非零结果仅在 DEBUG 构建中记录，不单独导致交接失败，也不修改原表中的校验和字段。签名、声明大小、引用范围和 BDB 结构检查仍是必须通过的条件。

[兼容性与验证](兼容性与验证.md)记录了一个 Arrow Lake 样本，其累计结果为 `0xDC`。源 fw_cfg 副本与客体内存中的完整 VBT 逐字节一致，且已记录的 Windows 设备检查和硬件操作通过。这说明交接保持了该样本的内容，非零结果在 ROM 搬运前已经存在。它的具体来源和根因仍未确定；这些结果不能把非零校验和推广为正常数据，也不能证明每个显示配置字段都正确。

这一处理策略参考了固定 [Linux 7.0 的 `intel_bios_is_valid_vbt()`](https://github.com/torvalds/linux/blob/028ef9c96e96197026887c0f092424679298aae8/drivers/gpu/drm/i915/display/intel_bios.c#L3064-L3106)：该函数检查 VBT 签名、表大小和 BDB 范围，没有读取或强制检查 `vbt_checksum`。这是对该函数校验行为的源码核实，不代表 Linux 认可任意损坏的表，也不代表本项目实现了 Linux 的全部解析逻辑。

因此，读取验证结果时需要区分三件事：数据结构允许安全访问、数据在交接中保持一致，以及显示配置适合实际硬件。校验和诊断和结构检查只覆盖其中一部分。

### 代码中的固定偏移从哪里来

这些数字来自数据格式约定。下表的偏移以 OpRegion 起点为基址，与前面的 PCI 配置空间 `0xfc` 属于两个不同对象：

| 偏移 | 长度 | 内容 |
|---|---|---|
| `0x00` | 16 字节 | `IntelGraphicsMem` 签名，恰好 16 字节 |
| `0x10` | 4 字节 | 基础区域大小，单位为 KiB |
| `0x14` | 4 字节 | 版本，如 `0x02010000` 表示 2.1 |
| `0x58` | 4 字节 | 哪些 mailbox 存在的位标记 |
| `0x3ba` | 8 字节 | RVDA：扩展 VBT 的位置 |
| `0x3c2` | 4 字节 | RVDS：扩展 VBT 的字节数 |
| `0x400` | 最多 6 KiB | 内嵌 VBT 区域 |

例如 `CopyMem(&Rvda, Blob + 0x3ba, sizeof Rvda)` 把 8 个字节复制到局部变量。X64 使用小端序，低有效字节放在低地址。通过复制读取可避开未对齐指针和结构体填充问题；整个缓冲区的长度必须先检查，才允许读取固定偏移。

验证相对偏移时，先判断 `Offset <= Size`，再判断 `Length <= Size - Offset`。如果直接判断 `Offset + Length <= Size`，恶意或损坏的巨大数值可能让加法溢出，从而绕过边界检查。这是普通 C 的整数规则在固件解析器中的具体应用。

这些检查能发现截断数据、越界引用和部分损坏。复杂 BDB 业务块、AIM 和具体显示配置的含义仍交给后续驱动处理，结构校验通过不直接说明某个显示接口能正常工作。

第二遍阅读时只追踪地址：`Blob` 指向哪里，RVDA 相对哪个基址，ASLS 何时接收地址。第三遍只看返回分支，确认失败是否发生在发布前、内存是否仍被设备引用。

## 7. EFI、ROM 和设备 ID 各自负责什么

EDK II 提供 UEFI 的开源实现、驱动库和构建工具。本项目固定使用 `edk2-stable202608`，上面的加载机制也以这一版源码为依据。

构建分为两个阶段。EDK II 将 C 文件与所需库编译、链接成 PE/COFF 格式的 `.efi`。封装工具再加入 PCI ROM 头、`PCIR` 数据结构、长度和对齐信息，生成 `.rom`。固件通过这些容器字段找到 EFI 载荷。

在 Mac 上交叉编译时，工具本身运行于 Mac，载荷目标仍是 X64 UEFI。ARM64 和 X64 都是 64 位架构，但指令集不同；交叉编译目标决定 EFI 能在哪种 CPU 环境执行。默认构建类型是 `RELEASE`，使用 `DebugLibNull` 关闭调试输出，源码中的 `DEBUG(...)` 此时不会产生日志。因此应分别检查工具能否运行、EFI 目标架构和子系统是否正确，以及 ROM 内嵌入的载荷是否与生成的 EFI 一致。

PCIR 中的 Vendor/Device ID 是 ROM 容器的设备标识元数据。运行时的 C 逻辑则决定程序实际访问哪个 PCI 接口。这两层可以分别设计：本项目的运行时逻辑不固定 Device ID；封装时仍显式提供目标设备的真实标识，由参数传入，避免把一个 SKU 写死在工具中。

固定 EDK II 的 PCI ROM 加载函数没有用 PCIR 的 Vendor/Device ID 做匹配判断；它检查 EFI code type、机器类型和子系统等，再加载映像。这一源码事实不等于“零 ID 是通配符”。`EfiRom` 明确拒绝 Device ID 为零，因为零在设备 ID 列表中用作终止标记。其他固件或平台 ROM 选择逻辑也可能有不同规则。

源码依据：[EFI ROM 加载条件](https://github.com/tianocore/edk2/blob/2970e5699ba6267f3384ffab20f96647578aebc8/MdeModulePkg/Bus/Pci/PciBusDxe/PciOptionRomSupport.c#L693-L718)、[EfiRom 的设备 ID 参数检查](https://github.com/tianocore/edk2/blob/2970e5699ba6267f3384ffab20f96647578aebc8/BaseTools/Source/C/EfiRom/EfiRom.c#L1008-L1039)。

不固定运行时 Device ID，让同一初始化逻辑不依赖某个 SKU 的编号。它的适用前提仍是本项目的 Arrow Lake、QEMU IGD 数据和寄存器约定；改变容器 ID 本身不会增加对其他平台的支持。

## 8. 怎样判断一份产物到底验证到了哪一步

把验证结论对应到实际发生的步骤，才容易定位问题：

| 验证层次 | 证据 | 能说明什么 |
|---|---|---|
| 编译、链接 | 构建完成，X64 PE/COFF 和 UEFI 子系统正确 | 源码与所用工具链可以生成 EFI |
| ROM 封装 | 头部、长度、边界正确，载荷与 EFI 一致 | 容器准确承载了该 EFI |
| 数据校验 | 校验函数对真实 blob 或构造样本返回预期结果 | 已检查到对应的数据结构条件 |
| 固件执行 | 入口执行、所属设备上下文成立、返回结果可确认 | 初始化路径实际走过 |
| 地址交接 | ASLS 读回一致，保留区的数据完整可读 | 地址与数据完成了交接 |
| 客体使用 | 操作系统驱动识别并使用设备，实际负载完成 | 该二进制在该客体配置下工作 |

合成用例便于覆盖数据边界和错误分支；真实 OpRegion 样本、固件加载和客体硬件操作分别提供其他层次的证据。仓库已记录的配置、通过结果和未覆盖项集中列在 [兼容性与验证](兼容性与验证.md)。新的平台或源码变更仍需要取得相应证据，不能从某个样本的通过直接推导其他环境也能工作。

阅读到这里，再回到入口沿一次成功路径读到底：取得自身设备、检查现有状态、准备数据、验证内容、发布地址、读回确认。最后对照错误分支，确认每条路径保留或释放了什么。这样能把普通 C 的控制流，与固件中跨越启动阶段的数据生命周期连接起来。
